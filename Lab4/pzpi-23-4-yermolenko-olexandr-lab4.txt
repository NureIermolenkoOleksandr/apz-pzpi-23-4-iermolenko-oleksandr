2 ЗАВДАННЯ
     
     Необхідно показати як можна масштабувати бекенд системи для роботи із великим навантаженням. Для цього, можна на вибір: - масштабувати сервер горизонтально - багато копій сервера виконують однакові функції для різних користувачів; - масштабувати сервер вертикально - різні мікросервіси виконують різні функції і масштабуються окремо одне від одного. З технічної точки зору, масштабування можна виконати так: - деплой сервера на Kubernetes кластер, разом із окремим load balancer-ом та базою даних. При цьому треба буде показати коректну роботу системи при збільшенні чи зменшенні кількості подів сервера чи окремих мікросервісів; - деплой в serverless середовище (AWS Lambda, Firebase Cloud Functions або аналогічне). Треба показати що система може зменшувати кількість активних інстансів до 0, збільшувати її зі збільшенням трафіку і все ще коректно функціонувати. - ваш власний спосіб показати що система може масштабуватись. На найвищий бал на цю роботу необхідно провести навантажувальне тестування за допомогою Gatling, JMeter, Locust чи іншого подібного інструмента і показати як зі збільшенням кількості серверів зростає кількість запитів на секунду яку витримує система

     3 ОПИС ВИКОНАНОЇ РОБОТИ
     
     Для реалізації високонавантаженої бекенд-частини системи контролю доступу Smart Lock було обрано підхід горизонтального масштабування за допомогою оркестратора Kubernetes (на базі локального кластера Docker Desktop).
     Основний бекенд розроблено на платформі Node.js (Express), взаємодія з реляційною базою даних PostgreSQL реалізована через Prisma ORM, а для обміну IoT-телеметрією з ESP32 використовується MQTT-брокер Mosquitto.
     Інструмент ШІ: Google Gemini 1.5 Pro
     Мета використання ШІ: Аналіз та діагностика інфраструктурних проблем у середовищі контейнеризації, оптимізація конфігурацій розгортання мікросервісів та усунення мережевих помилок у взаємодії компонентів системи Smart Lock.
Початковий промпт (Prompt): "Analyze common networking issues in a Docker + WSL2 + Kubernetes environment where frontend cannot reach backend API (NodePort). The system uses Locust for load testing, but requests fail with Status 0. Provide possible causes related to port binding, firewall rules, service configuration, and cluster networking."
     Внесок автора: На основі отриманих рекомендацій було виконано діагностику інфраструктури системи Smart Lock, виявлено та усунуто проблеми мережевої взаємодії між Windows-хостом, WSL та Docker-контейнерами. Було налаштовано коректну роботу NodePort-сервісів, перевірено конфігурацію Kubernetes-подів та оптимізовано маршрутизацію запитів між тестовим навантажувачем Locust і серверною частиною API.
1. Контейнеризація та розгортання в Kubernetes 
     Усі компоненти системи були описані у маніфестах Kubernetes (k8s-deployment.yaml).
     База даних та брокер: Для PostgreSQL та Mosquitto створено окремі Deployment (по 1 репліці) та внутрішні ClusterIP Service (порти 5432 та 1883 відповідно).
     API Сервер: Налаштовано базовий Deployment на 3 початкові репліки. Вирішення стану гонитви (Race Condition): Під час холодного старту кластера було виявлено проблему CrashLoopBackOff для подів API. Оскільки Kubernetes запускає контейнери одночасно, команда npx prisma db push виконувалася до повної ініціалізації PostgreSQL, що призводило до падіння Node.js. Проблему вирішено механізмом відкладеного старту та командою kubectl rollout restart deployment.
2. Налаштування мережі та відмова від Port-Forward 
     Початкова спроба тестування через kubectl port-forward виявилася невдалою: при навантаженні понад 10 RPS тунель не витримував і розривав з'єднання (connection reset by peer, Status 0 у Locust). Для забезпечення стабільної пропускної здатності тип сервісу smart-lock-api-service було змінено на NodePort із фіксованим зовнішнім портом 30081. Це дозволило пустити трафік напряму через віртуальний комутатор Docker, оминаючи нестабільні тимчасові тунелі.
3. Горизонтальне масштабування (HPA) 
     Для автоматичного керування кількістю подів бекенду під навантаженням налаштовано Horizontal Pod Autoscaler (HPA). Виділено ліміти ресурсів: CPU (requests: 250m, limits: 500m), Memory (requests: 256Mi, limits: 512Mi). Цільове використання CPU: 60%. Мінімальна кількість реплік: 2, максимальна: 10. При зростанні кількості запитів Kubernetes автоматично створює нові поди smart-lock-api, розвантажуючи існуючі екземпляри.
4. Навантажувальне тестування (Locust). Розроблено скрипт locustfile.py, який імітує реальну поведінку клієнтів системи доступу:
     - Реєстрація користувача та отримання JWT-токена.
     - Паралельне виконання GET-запитів до ендпоінтів /api/dashboard, /api/devices. Після переходу на NodePort система успішно витримала навантаження (було протестовано до 50 одночасних користувачів з високим spawn rate) без помилок з'єднання. Тестування також підтвердило коректну роботу Role-Based Access Control: звичайні користувачі, згенеровані Locust, справедливо отримували статус 403 Forbidden при спробі доступу до журналу аудиту (/api/logs).
     
     
     
      
      
      


      
     4 ВИСНОВКИ
       
     У ході виконання лабораторної роботи було успішно налаштовано горизонтальне масштабування бекенду системи Smart Lock у середовищі Kubernetes. Застосування Horizontal Pod Autoscaler дозволило системі автоматично створювати нові репліки API при зростанні навантаження на процесор.
     Навантажувальне тестування за допомогою Locust підтвердило, що використання тимчасових засобів дебагінгу (таких як port-forward) є критичним вузьким місцем при високих навантаженнях (спричиняє Status 0). Перехід на нативні механізми маршрутизації Kubernetes (NodePort) повністю усунув втрати пакетів. Спроектована архітектура з 3-10 екземплярами Node.js API, що працюють із єдиною базою PostgreSQL, демонструє стабільність, відмовостійкість та готовність до обробки сотень одночасних запитів від IoT-пристроїв та користувачів.
