Харків 2026

     1.1 Мета роботи
     Ознайомитися з архітектурними підходами у сучасних складних програмних системах на прикладі GitHub, проаналізувати структурну організацію платформи, масштабування, взаємодію компонентів і застосовані архітектурні стилі.
     
     1.2 Загальна характеристика GitHub
     GitHub це платформа спільної розробки програмного забезпечення навколо системи контролю версій Git. Вона об’єднує розміщення репозиторіїв, issues, pull requests, code review, Actions, Packages, засоби безпеки, пошук та інтеграційні API.
     Платформа починалася як Ruby on Rails-застосунок з однією базою MySQL. Подальший розвиток відбувався еволюційно: ядро-моноліт було збережено, але навколо нього з’явилися спеціалізовані сервіси, черги, кеші, окремі системи зберігання й пошуку. Тому GitHub доцільно розглядати як гібридну сервісно-орієнтовану систему.
     
     1.3 Архітектура верхнього рівня
     Клієнтами GitHub є браузери, Git-клієнти, мобільні застосунки та сторонні інтеграції. Вони працюють через HTTPS, SSH, REST API або GraphQL API. Після балансування запит потрапляє до вебрівня, де виконуються автентифікація, авторизація та прикладна логіка.
     
     1.4 Організація даних
     Git-репозиторій містить content-addressed об’єкти: commits, trees і blobs. Вони мають інші характеристики доступу, ніж дані вебплатформи. Користувачі, дозволи, issues, pull requests та налаштування зберігаються як реляційні метадані. Таке розділення дає змогу незалежно оптимізувати зберігання коду і бізнес-даних.
     MySQL залишається основною реляційною СУБД GitHub. Архітектура еволюціонувала від одного екземпляра до багатьох кластерів із primary та replicas. Для подальшого масштабування GitHub застосовує розділення даних між кластерами. Перевагами є горизонтальне масштабування та ізоляція відмов, а недоліками є складніша маршрутизація, міграції і транзакції між розділами.
     Push є ключовим сценарієм GitHub. Спочатку Git-рівень приймає об’єкти та оновлює refs. Після цього необхідно запустити десятки залежних дій: перевірки, Actions, webhooks, оновлення pull requests, сповіщення та індексацію. GitHub Engineering повідомляє, що в моноліті на push безпосередньо реагували понад 60 фрагментів логіки, якими володіли 20 сервісів.
     Щоб критичний шлях не залежав від усіх споживачів, події передаються у фонову обробку. Такий підхід підвищує доступність і пропускну здатність, але вимагає ідемпотентності, повторних спроб, контролю черг і спостережуваності.
     
     1.5 Інтеграційна архітектура
     API створює стабільну межу між GitHub та зовнішніми клієнтами. REST організований навколо ресурсів і HTTP-операцій. GraphQL дає клієнту змогу вибрати потрібні поля та отримати пов’язані дані одним запитом. Для обох підходів критичними є автентифікація, авторизація, версіонування і rate limiting.
     Webhook реалізує подієво-орієнтовану інтеграцію: після події GitHub надсилає HTTP POST на адресу отримувача. Це зменшує потребу в polling. Отримувач повинен швидко підтвердити доставку, перевірити HMAC-підпис, обробляти дублікати й переносити важку роботу у власну чергу.
     GitHub Actions використовує workflow-файли YAML. Подія створює запуск workflow, планувальник формує jobs, а runners виконують steps. Hosted або self-hosted runners ізолюють виконання користувацького коду від основного вебзастосунку. Логи, кеші та артефакти мають власний життєвий цикл.
     
     1.6 Масштабування, надійність і безпека
     Масштабування досягається балансуванням запитів, реплікацією читання, partitioning даних, кешуванням, асинхронною обробкою та незалежним масштабуванням сервісів. Надійність підтримують репліки, failover, повторні спроби, ідемпотентність і моніторинг.
     Безпека проходить крізь усі рівні: автентифікація, перевірка прав на репозиторії, захист токенів, ізоляція runners, підпис webhook-повідомлень та аудит дій. Важливо, що авторизація має перевірятися на сервері для кожної операції, а не лише в інтерфейсі.
     
     1.7 Висновки
     GitHub демонструє еволюційну гібридну архітектуру. Платформа не відмовилася від монолітного ядра, але винесла навантажені та спеціалізовані функції в окремі сервіси. Короткий синхронний шлях, асинхронні події, розділення Git-даних і метаданих, реплікація та partitioning забезпечують масштабованість. Основною ціною є операційна складність і необхідність керувати узгодженістю розподілених компонентів.
